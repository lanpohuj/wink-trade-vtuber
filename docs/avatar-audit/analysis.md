## Как устроен фактический код

Несмотря на старые записи про VRM в AGENTS.md, резервный `avatar.js` загружает
именно FBX `model/shibahu.fbx` через локальный FBXLoader. Подменять этот rig на VRM
для задачи не нужно. Его координаты и оси отличаются от нормализованного гуманоида.

| Узел | Ответственность |
|---|---|
| `winky/web/avatar.js:84` | Разделение морфов по Y=138.3: рот отделён от глаз |
| `avatar.js:152` | ShibahuFBXController: исходные углы и позиции костей, алиасы, пальцы и таймеры |
| `avatar.js:247` | Целевые вращения относительно rest pose, сглаживание quaternion slerp |
| `avatar.js:317` | Тело, дыхание, голова, плечи, руки, пальцы, уши, хвост и спецдействия |
| `avatar.js:764` | Лицо, моргание, RMS-артикуляция; часть лицевых целей повторяется в теле |
| `avatar.js:894` | Эмоции одновременно могут запускать действия |
| `avatar.js:999` | Таймеры, вес речи, последовательная автоматическая петля флирта |
| `avatar.js:1191` | winkySpeak применяет эмоцию; сам звук здесь не запускается |
| `avatar.js:1233` | RMS задаёт говорение и продлевает speechHoldTimer на 0.85 с |
| `winky/tts.py:1453` | SpeechItem уже содержит текст, язык, категорию, событие, emotion/action, bank_id |
| `tts.py:2241` | Единый afplay, отсчёт monotonic, RMS каждые 50 мс, завершение в finally |
| `winky/app.py:1050` | Мост Python → JS: речь, громкость, действие и эмоция раздельными вызовами |
| `winky/chat_router.py:560` | Вход, подписка, подарок и лайки; готовые записи или запасные сценарии |
| `winky/director.py:180` | Подготовка ответа чату в фоне; передача готового ответа единой очереди |
| `winky/chat_style.py:76` | Типы локальных ответов, но возвращаемый тег у всех `[wink]` |
| `winky/voice_bank.py:85` | Выбор записи с условиями, приёмкой, исключениями и ротацией |

Действующая цепочка: событие → выбор/подготовка фразы → SpeechItem → afplay →
on_action + on_emotion + on_speak → модель; RMS идёт отдельными короткими вызовами.
До браузера не доходит полный объект фразы с идентификатором, категорией и временем.
Форманты сохраняются в setAudioFormants, но updateFace их не использует: фактический
липсинк здесь RMS + процедурное чередование форм, не распознавание фонем.

## Найденные причины дефектов

1. **Повторный запуск одного действия.** `tts.py:2303–2310` вызывает действие,
   эмоцию и речь. `app.py:487` снова превращает ряд эмоций в действия; оконный
   winkySetEmotion и winkySpeak делают это ещё раз. При win возможны четыре
   установки cheer, при wave — несколько установок waveTimer. Дублирование
   подтверждено цепочкой вызовов; оно не означает четыре последовательных танца.
2. **Смысл заменён общей эмоцией.** Лайки явно используют cheer, подписки/подарки —
   dance, excited в запасном маршруте чата — cheer. Обычная речь дополнительно
   переводит обе руки из позы покоя в одну общую разговорную позу (`avatar.js:708`).
   Поэтому неверно объяснять все высокие поднятия рук только RMS: высокие позы
   приходят главным образом из назначенных действий.
3. **Большие пальцы у лапок.** В ветке neko_paws весь rightFingerBones/leftFingerBones
   получает один Z=-0.35, включая Thumb1–3. У большого пальца другие исходные оси;
   одинаковый поворот не складывает его вдоль кулака.
4. **Поцелуй во второй фазе превращается в открытую улыбку.** После 1.35 с код
   обнуляет face_mesh9 и включает face_mesh1=0.88. Кисть и предплечье также получают
   дополнительное колебание от общего t*7.0, а не от фазы жеста. Это соответствует
   замечанию владельца о губах и неестественном движении ладони.
5. **Нет явного конца фразы в аватаре.** Ноль RMS не сообщает, пауза это или конец.
   Тело остаётся в весе речи через hold, хотя afplay уже мог завершиться.
6. **Возможное залипание эмоции.** Если emotionResetTimer истекает во время речи,
   условие сброса не выполняется, а в следующий кадр ветка timer>0 уже не зайдёт.
   Такая эмоция может блокировать автоматическую idle-петлю. Вывод из кода;
   в рабочем приложении этот сценарий в рамках задачи не воспроизводился.
7. **Расхождение названий.** triggerAction('wave') не равен wave(), а 'think' не
   равен 'thinking'. Часть путей только меняет таймер без нужной отдельной позы.
8. **Несколько владельцев одной цели.** Танец повторно записывает hips/spine/head,
   а лицо задаётся и в updateBodyPhysics, и в updateFace. Итог зависит от порядка
   сглаживания; последующее добавление жестов прямо в этот блок повышает риск.
9. **Автоматический флирт — фиксированная последовательность.** Поцелуй, лапки,
   бедра и приближение идут по кругу через короткие интервалы без смыслового
   контекста. Объявленные microHabit поля практически не получают новых привычек.
10. **Исторические описания морфов расходятся с текущей хирургией.** Нельзя брать
   номер face_mesh из старой памятки и назначать новую мимику без измерения вершин.
   Новая версия не переопределяет операцию разделения глаз и рта или материалы.

## Что подготовлено в стенде

Кандидат — адаптер поверх точной копии резервного контроллера. Это не новая модель
и не замена существующей пластики. Масштаб, свет, материалы и хирургия лица сохранены.

- Обычная речь не поднимает руки сама. Отдельные небольшие движения: кивок,
  любопытный наклон, объяснение одной рукой, поклон благодарности, мягкая радость;
  предусмотрен спокойный вариант без дополнительного жеста и старое приветствие.
- Политика выбирает профиль по категории и chat_kind; для свободного ответа есть
  явный intent. Его приоритет выше общей эмоции. Лайк не превращается в победу,
  смена пары — в празднование, вопрос скептика — во флирт из-за `[wink]`.
- Один идентификатор воспроизведения → один выбор движения. Повтор начала не
  перезапускает позу. Конец старого ID не завершает новую фразу. Варианты чередуются
  без непосредственного повторения, а не меняются при каждом обновлении RMS.
- Начало берётся из фактического browser audio playing, фаза — из currentTime,
  завершение/остановка явно переводит кандидата в покой. RMS вычисляется из этой
  же записи и управляет ртом. Это проверка механизма в браузере, не замена afplay.
- **Качание бёдрами сохранено.** Ветка hip_groove не переписывалась.
- **Лапки:** для каждой руки отдельные углы Thumb1–3. Приблизительная конечная
  точка большого пальца находится в 0.10/0.22 см от выбранной внешней точки у
  указательного пальца против примерно 5–6 см у исходника. Это измерение rig,
  не доказательство отсутствия любого пересечения кожи во всех кадрах.
- **Поцелуй:** подготовка, касание, отправка и опускание заданы плавными фазами;
  убрано колебание ладони. Сложенные губы сохраняются при отправке. Три небольших
  сердечка появляются у проекции рта в момент отправки и исчезают самостоятельно.
- Танец с поднятыми руками и cheer оставлены только для отдельного разбора.
  Большая автоматическая idle-петля в кандидате отключена; дыхание и исходная
  спокойная пластика продолжают работать.

Каталог стенда: 1543 существующих записи из активного lively_v3 и базового lumean
на момент проверки. Это число файлов для просмотра, не обещание доступности всех
вариантов в любом контексте реального эфира. Приёмка аудио и история не изменены.

## Как переносить после просмотра

В основном приложении ничего из следующего пока не реализовано. До переноса нужно
оценить в движении пальцы, ладонь и губы вместе с владельцем; дефектный танец с
поднятыми руками не включать в автоматический выбор.

1. Добавить в Winky отдельное событие жизненного цикла речи из существующего
   SpeechItem: speech_id, категория/intent, emotion, duration, audio position,
   RMS и причина конца. Один источник времени — monotonic отсчёт afplay.
   Событие начала только после успешного запуска проигрывателя, конца — в finally.
2. В этой новой ветке единственный планировщик выбирает жест. Эмоция управляет
   лицом, громкость — артикуляцией. Сохранить единый SpeechController и защиту
   очереди; анимации не должны блокировать текущую речь или торговлю.
3. Для лапок и поцелуя отводить подходящие короткие моменты между предложениями
   или после фразы. При речи артикуляция имеет приоритет над губами поцелуя.
   Не подменять фонемную синхронизацию приблизительным временем слов: текущий
   RMS не содержит точных словесных отметок.
4. Сохранить исходник отдельным переключаемым режимом. Сначала проверить нативный
   WKWebView: прозрачность, нагрузку на Mac/OBS, короткие/длинные фразы, RU/EN,
   потерю окна, Stop, ошибки afplay, очередь и длинный сеанс. Затем отдельно
   реальный TikTok. Тест из браузера не равен этой приёмке.

Полная замена корпуса анимаций или новой модели здесь не требуется. Более
выразительный танец с руками следует делать отдельным следующим образцом после
правильной постановки предплечья, кисти и пальцев; красивые названия не доказывают
анатомически правильное движение.
